# BUG-005 — Security Rules permitiam leitura direta de fatores

**Origem:** OBS-05 do registro do PO (01/11/2026)
**Critério afetado:** CT-M02.3 e CA-04
**Severidade:** Alta — segunda barreira existia no papel, não verificada
**Estado:** **Fechado** — deny-all puro no PR #30
**Responsável:** DevOps (#13) + QA (#24)

## Passos para reproduzir (antes da correção)

1. Com o emulador populado, ler `/fatores` direto pelo SDK cliente **sem token**.
2. Repetir autenticado, tentando ler `/tenants/{outraEmpresa}/...`.

## Esperado

Nenhum cliente acessa o Firestore diretamente. Toda leitura passa pela API, que
autoriza por claim.

## Obtido (antes da correção)

A leitura anônima de um fator retornava **200**. Existia também regra por claim em
`/tenants`, duplicando a autorização que a API já faz.

## Correção aplicada

Rules reduzidas a deny-all puro, sem nenhuma exceção:

match /{documento=**} { allow read, write: if false; }

Duas permissões caíram, com justificativa:

| Regra removida | Motivo |
| --- | --- |
| `match /fatores/{versao}` — leitura pública | O frontend não lê fatores direto; usa `GET /v1/fontes`. Porta aberta sem uso é superfície de ataque. |
| `match /tenants/{tenantId}/**` por claim | Duplicava a autorização da API. Duas fontes de verdade sobre permissão divergem com o tempo. |

A API continua funcionando porque o **Admin SDK ignora Security Rules por definição**.

## Verificação — 9 casos no emulador

`qa/test_deny_all.py`, rodando no job `deny-all` do CI com token real do Auth Emulator:

- anônimo não lê / não escreve / não apaga → 403
- autenticado não lê / não escreve → 403
- usuário de outra empresa não lê → 403
- autenticado não lê `/fatores` direto → 403
- Admin SDK continua lendo e escrevendo → 200 *(contrapeso: prova que o produto não quebrou)*
- API responde com dado semeado → 200

## Nota

Sem os dois últimos casos, "deny-all" poderia significar apenas "o produto parou de
funcionar". Uma regra que quebra o produto não é segurança, é indisponibilidade.
